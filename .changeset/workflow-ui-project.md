The studio reads the project: workflow.config.ts default-exports `defineConfig({...})` from `@shware/workflow`, and its `workflows`, `segments`, `actions`, `templates` registries, `title` and `emails` envelope are what the studio shows — nothing is scanned — compiled with `compileConfig`, so the lists match what the Worker deploys; a `ConfigCompileError` (or a config that fails to load) is shown in place of the views with the workflow and node it names. The config is evaluated on the dev server (Vite SSR, with source maps on, so captured node positions are lines on disk); the browser receives the compiled IR as JSON and imports only the two template registries from the modules that export them, never the config, its contract, runtime settings or host dependencies. Adding or removing a workflow or template in the registration list updates over HMR. The stats source is an optional `workflow.stats.ts` (`defineStats`, or `--stats <path>`). `ResolvedStudioConfig.workflows` holds compiled `WorkflowIR` keyed by workflow name, `segments` holds `SegmentIR`, and it gains `error` and `emailDefaults`; the `@jridgewell/trace-mapping` dependency is gone.
