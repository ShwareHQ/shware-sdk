Schema-driven templates: `emailTemplate({ title, description, props, subject, preview, component })` and `pushTemplate({ title, description, props, preview, content })`, exported from the core entry (no React). The required Zod `props` (a strict object of string / number / boolean / enum / literal fields, optionally `.optional()`) is the only source of the props type — DSL arguments, preview and the component/content parameter derive from it — and is enforced at run time: the preview at declaration, and every send after user refs resolve, through a new `MessageValidator` port that `journeyWorker` builds from its registries (`registryValidator`), so normal senders, custom senders and the dev log all see only parsed props, and a push is validated before its first device. Failures throw `TemplateValidationError` (`phase: 'props'` — component/content never called; `'content'` — the notification returned is invalid) with the instance and node in the message, and the Cloudflare step ends without retries. `templates<Emails, Pushes>()` types both registries (`t.push(key)`). Registries hold only these definitions: the legacy module shapes (a default-exported email component with a `{{ user.x }}` subject, push strings with `{prop}` placeholders), `emailSubject`, `fillSubject`, `fillProps` and `CfEmailSender`'s profile lookup are removed. The renderers render email components as elements (hooks and context work) and send the subject and the push content exactly as the template returns them.
