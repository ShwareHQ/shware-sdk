Email unsubscribes are per topic, and the engine is the one record of them.

- **Topics live in the contract.** `defineContract({ events, profile, subscriptions: { email: ['promotions', 'newsletter'] } })` declares the email topics (ids only, `as const`-typed): `contract.topics.email`, `EmailTopic<typeof contract>`, and the compiled bundle carry the list.
- **Every email template says what it is.** `emailTemplate` takes `topic: '<id>'` or `transactional: true` (the literal, never a boolean); leaving both out, giving both, or giving a transactional template an `unsubscribeUrl` is a type error and a compile error. `compileConfig` refuses a topic the contract does not declare, naming the template and the declared list, and `defineConfig({ contract, templates })` refuses it in the editor. A transactional email resolves to no unsubscribe link and no `List-Unsubscribe` headers whatever `email.unsubscribeUrl` says; the old rule "no unsubscribe URL means a receipt" is gone. `EmailTemplate` and `ResolvedEmail` carry `topic: string | null`.
- **The IR and the reporting tables carry the topic.** An email message node has `topic` (null for transactional), so every workflow that sends email gets a new `contentHash` — in-flight instances keep running their pinned version, and `plan` reports the change once. The `message` table gains a nullable `topic` column, written for email copies.
- **Suppression is per topic.** `suppression` gains a nullable `topic` column: a row with a topic is an opt-out from that topic, a row with null is an opt-out from all email — which is what every row from before means, so the migration needs no data step. The `(user_id, channel)` primary key becomes a `UNIQUE NULLS NOT DISTINCT (user_id, channel, topic)` constraint (Postgres 15+); regenerate the drizzle file and migrate before deploying. `JourneyStore.isSuppressed(userId, channel, topic?)` is true for the topic's row or the channel's; `listSuppressions` and `updateSuppressions` are new. A topic email step is skipped on either; a transactional step never checks; `reachable('email')` reads the all-email row only, so a single-topic unsubscribe does not fire `exitWhen: not(reachable('email'))`. Push is untouched. `forgetUser` now erases the user's suppression rows with the rest: the tombstone keeps the id from ever being sent to again.
- **Tracking routes.** `POST /t/u/<message>` (RFC 8058 one-click, and the page's first button) opts out of the email's topic; `?scope=all` (the page's second button) of every email. The confirmation page names the topic. A transactional copy answers 404 on every `/t/u` variant. `onUnsubscribed` receives `{ topic, all }`, and the host wakes the `reachable('email')` waits only for `all`. `JourneyReporting.recordUnsubscribe(messageId, at, scope?)` answers `{ userId, topic }`; `lookupMessage` is new.
- **Subscriptions API.** `GET /subscriptions/:userId` answers `{ email: { all, topics } }` (`true` = subscribed); `PUT /subscriptions/:userId` takes a partial `{ email?: { all?, topics? } }`, validated against the deployed bundle's topics (400 with field paths), 410 for an erased user, and answers the new state; a change of `all` wakes the email-reachability waits. `JourneyClient.getSubscriptions(userId)` and `setSubscriptions(userId, patch)` are typed by the contract and refuse an undeclared topic before the request.

Migrating: add `topic` or `transactional: true` to every `emailTemplate`; add `subscriptions: { email: [...] }` to `defineContract` (and pass the `contract` to `defineConfig` wherever topic templates are registered); regenerate the drizzle schema and migrate the `suppression` and `message` tables.
