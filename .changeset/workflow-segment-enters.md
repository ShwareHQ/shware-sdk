A segment trigger only looks forward, and is now spelled `trigger.enters(segment)`.

- **The people already in a segment no longer enter it.** A segment trigger starts a journey when a user goes from not matching to matching, which the engine reads off the membership it keeps. A segment with no membership yet — new in this deploy — had everyone who already matched read as entering: shipped together with its trigger, the next sweep started a journey for the whole existing audience, while the same trigger added to a segment deployed earlier started none. Now a segment a deploy brings in new, or with a changed condition (its own, or that of a segment it is built on), is seeded first: until a sweep has been through every user, whoever matches is recorded as a member and starts nothing; from then on a user who newly matches enters. Redeploying an unchanged bundle does not start the seeding over. **What changes for you:** a deploy no longer starts journeys in bulk — not for a new segment with its trigger, and not for the users an edited condition newly covers. During the seeding (one sweep) a user who genuinely enters is recorded without a journey too. To reach everyone who is in a segment, name it in a condition instead (a trigger's `filter`, a `branch`): that asks each user at that moment and is unaffected.
- **`trigger.enters(segment)`** is the trigger's name; `trigger.segment` is kept as a deprecated alias. The IR is unchanged (`type: 'segment'`), so no content hash moves.
- **Migration required:** `segment` gains a nullable `seeding_since` column — regenerate the drizzle file (`workflow-ui generate`) and run the migration before the new version serves; `POST /bundle/deploy` answers 503 without it. No data step: segments already deployed are taken as seeded.
- `JourneyStore` gains `seedingSegments()` and `finishSeeding()`, and `SegmentTriggerRoute` an optional `seeding`. The AWS sweep has two more durable steps (`sweep:seeding`, `sweep:seeded`).
