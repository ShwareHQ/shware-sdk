# @shware/workflow

## 6.1.0

### Minor Changes

- ebda232: Message-scoped subscription management, for an email preference page that works without a sign-in.

  - **`email.preferencesUrl`** names the app's preference page. A topic email sent with reporting on (a message id exists: the same condition as the one-click header) renders with `useEmailContext().preferencesUrl`, that page with the copy's message id as the `m` query parameter (any query the page already has is kept); a transactional email, or a send without reporting or without the config, has none, so a layout renders the link conditionally like `unsubscribeUrl`. It is tracked as an ordinary click, never as an unsubscribe, and the config refuses a `preferencesUrl` that shares its origin and path with `email.unsubscribeUrl` or a template's own. `GET /preview` renders it with the placeholder `PREVIEW_MESSAGE_ID`, so the footer shows.
  - **`GET` / `PUT /subscriptions/by-message/:messageId`** (bearer-protected, beside `/subscriptions/:userId`) read and set the recipient's subscriptions by one of their copies: the answer is the user endpoint's `{ email, push }` plus `message: { channel: 'email' | 'push', topic }`, the copy the page was opened from; the `PUT` takes the same patch. An id that names no copy — never sent, not a UUID, or erased with its user — or a transactional copy answers 404, the rule `/t/u` applies. The message id is the capability, so the app proxies and rate-limits the routes behind its own API.
  - **`JourneyClient.getSubscriptionsByMessage(messageId)`** and **`setSubscriptionsByMessage(messageId, patch)`**, typed like the user pair (`MessageSubscriptions<T>`, `MessageOrigin<T>`).
  - For custom hosts: `resolveEmail(template, config, { messageId })` builds the link, `EmailRenderer` takes an optional third argument `{ messageId }` that `EmailSender` fills from `MessageTracking.messageId` (new, set by `reportingObserver` for emails), and `ResolvedEmail` / `RenderedEmail` carry `preferencesUrl`. `assertUnsubscribeUrl` is now `assertHttpUrl` (the old name stays as an alias).

## 6.0.0

### Major Changes

- 3368cd5: Email and push opt-outs are per topic, and the engine is the one record of them.

  - **Topics live in the contract, independent of channels.** `defineContract({ events, profile, subscriptions: { topics: ['promotions', 'newsletter'] } })` declares the subscription topics — content categories, not channels (ids only; a plain array literal keeps the literals): `contract.topics` (the readonly list), `contract.isTopic`, `Topic<typeof contract>` and the compiled bundle (`subscriptions.topics`) carry the list. A user opts out of a topic per channel: the preference page is topic × channel.
  - **Every email and push template says what it is.** `emailTemplate` and `pushTemplate` take `topic: '<id>'` or `transactional: true` (the literal, never a boolean); leaving both out, giving both, or giving a transactional email an `unsubscribeUrl` is a type error and a compile error. `compileConfig` refuses a topic the contract does not declare, naming the template and the declared list, and `defineConfig({ contract, templates })` types both registries by the contract's topics. `templatesFor(contract)` gives the same factories with the topic typed by the contract, so an undeclared topic is an error at the template's own `topic` line (in the editor, and when the module loads), the form to use wherever a contract exists. A wrong kind reads as words in the editor: the slots nothing fits are string-literal types ("give either 'topic' or 'transactional: true', not both"; "a transactional email has no unsubscribe link, so it takes no 'unsubscribeUrl'"), and a template that says neither is told so by the property it is missing. A transactional email resolves to no unsubscribe link and no `List-Unsubscribe` headers whatever `email.unsubscribeUrl` says; the old rule "no unsubscribe URL means a receipt" is gone. `EmailTemplate`, `PushTemplate` and `ResolvedEmail` carry `topic: string | null`.
  - **The IR and the reporting tables carry the topic.** An email or push message node has `topic` (null for transactional, which tells it from IR compiled before topics), so every workflow with an email or push step gets a new `contentHash` — in-flight instances keep running their pinned version, and `plan` reports the change once. `OutboundMessage.topic` is set for email and push copies, and the `message` table gains a nullable `topic` column, written for both.
  - **Suppression is per topic and channel.** `suppression` gains a nullable `topic` column: a row with a topic is an opt-out from that topic on that channel, a row with null is an opt-out from the whole channel — which is what every row from before means, so the migration needs no data step. The `(user_id, channel)` primary key becomes a `UNIQUE NULLS NOT DISTINCT (user_id, channel, topic)` constraint (Postgres 15+); regenerate the drizzle file and migrate before deploying. `JourneyStore.isSuppressed(userId, channel, topic?)` is true for the topic's row or the channel's; `listSuppressions` and `updateSuppressions` are new. A topic email or push step is skipped on either (a push once per step, before any device); a transactional step never checks; `reachable('email')` and `reachable('push')` read the channel-wide row only, so a single-topic opt-out does not fire `exitWhen: not(reachable(...))`. `forgetUser` now erases the user's suppression rows with the rest: the tombstone keeps the id from ever being sent to again.
  - **Tracking routes (email only).** `POST /t/u/<message>` (RFC 8058 one-click, and the page's first button) opts out of the email's topic; `?scope=all` (the page's second button) of every email. The confirmation page names the topic. A transactional copy answers 404 on every `/t/u` variant. `onUnsubscribed` receives `{ topic, all }`, and the host wakes the `reachable('email')` waits only for `all`. `JourneyReporting.recordUnsubscribe(messageId, at, scope?)` answers `{ userId, topic }`; `lookupMessage` is new. Push has no tracking route: the app records its opt-outs through the subscriptions API.
  - **Subscriptions API covers both channels.** `GET /subscriptions/:userId` answers `{ email: { all, topics }, push: { all, topics } }` (`true` = subscribed; every channel lists every declared topic); `PUT /subscriptions/:userId` takes a partial `{ email?: { all?, topics? }, push?: { all?, topics? } }`, validated against the deployed bundle's topics (400 with field paths), 410 for an erased user, and answers the new state. `all: true` clears only the channel-wide opt-out; a topic opted out on its own stays off until the patch names it, and an answer's `all: false` masks every topic of the channel. A change of `email.all` wakes the `reachable('email')` waits, of `push.all` the `reachable('push')` waits (the in-app opt-out App Store Review Guideline 4.5.4 requires for marketing pushes). `JourneyClient.getSubscriptions(userId)` and `setSubscriptions(userId, patch)` are typed by the contract (`Subscriptions<T>`, `SubscriptionsPatch<T>`, `ChannelSubscriptions<T>`) and refuse an undeclared topic before the request.

  Migrating: add `topic` or `transactional: true` to every `emailTemplate` and every `pushTemplate` (declare them through `templatesFor(contract)` where a contract exists); declare the topics as `subscriptions: { topics: [...] }` in `defineContract` and pass the `contract` to `defineConfig` wherever topic templates are registered; read `push` as well as `email` from `getSubscriptions`; regenerate the drizzle schema (`workflow-ui generate` now writes a file the formatter leaves alone) and migrate the `suppression` and `message` tables.

## 4.0.0

### Major Changes

- da8ebed: Close the correctness gaps the review found in the durable runtime, the store and the host. Regenerate the drizzle schema (`workflow-ui generate`) and migrate Postgres before deploying; recreate D1 databases; Workers drop the `WORKFLOW_KV` binding.

  - **Waits.** A `waitUntil` or goal tail that genuinely timed out after the instance was evicted (any `wrangler deploy`) no longer ends the journey as `failed`: the timeout verdict is taken against the deadline the interpreter checkpointed, not a clock read on the live attempt. `EngineStep.waitForWake(name, { timeoutMs, deadlineMs })` replaces `waitForWake(name, timeoutMs)`, and `sleepUntil` is gone from the port — the interpreter checkpoints the remaining time and sleeps, so a `timeWindow` replayed after its target no longer throws. When a wait exhausts its wake budget it now sleeps to its deadline and checks once more, instead of being read as a timeout.
  - **Non-retryable errors on Cloudflare** keep the `NonRetryableError` name the engine recognises, so a template or contract refusal, or a provider's 4xx, ends the step at once instead of retrying five times.
  - **Scoped profile wakes.** A property condition subscribes to `$profile_updated:<property>` and `/identify` wakes only the properties it patched; an unsubscribe wakes waits on the email address, so `exitWhen: not(reachable('email'))` takes effect at once.
  - **Event ids are per user.** The unique key on the event log is `(user_id, event_id)`; two users reusing one id no longer lose an event.
  - **Erasure is final, and mutually exclusive with running.** `/users/forget` records a tombstone first; every write about the user — events, profile, devices, entries, subscriptions, reporting — is conditional on it in the same SQL statement, so a write racing the erase is refused rather than resurrecting the user, and `/events`, `/identify` and `/devices` answer 410 for an erasing or erased user for good. On Postgres the four control points — `requestErasure`, `forgetUser`, `enterJourney` and the runner's admission — serialize per user on an advisory lock. A runner admits itself (`JourneyStore.admitInstance`, recorded as `entry.admitted_at`) on every invocation and every replay, before its first observable effect: an instance created late, after the erase, exits without running; `erased: true` means every admitted instance was confirmed stopped, un-admitted entries can never run, and the data is gone for good: every write about a user runs in the user's locked transaction, the lock the tombstone takes, so a write either committed before the tombstone and is deleted by the erase, or waits for the lock and is refused — no time window, no second pass. On AWS every stop judgment obeys one drain: the sweep's reconcile keeps a stopped execution's entry `running` until `stopDrainMs` has passed since the stop was first observed, so an erasure never completes early. Suppressions (unsubscribes) survive an erasure. `runningInstances` reports `{ instanceId, admitted }`.
  - **Input checks.** A body that is not JSON answers 400; `ts` must be a non-negative integer no later than five minutes ahead; `/identify` values must be scalars or null. The host has an error boundary: an unexpected failure answers 500 instead of escaping `fetch`.
  - **Production needs `API_TOKEN`.** A host whose `ENVIRONMENT` resolves to `production` answers 503 to everything but `/health` and `/t/...` until it is set; the bearer is compared in constant time.
  - **D1 keeps the IR in a `workflow_ir` table**, not in KV: an instance started in another colo right after a deploy always finds its IR. `D1JourneyStore` takes only the database; `JourneyEnv.WORKFLOW_KV` and `KVNamespaceLike` are removed.
  - **The deploy check verifies unique indexes**, not only columns, so a database missing an `ON CONFLICT` target is refused at deploy rather than at the first event.
  - **AWS.** A `$workflow.run` input must match a start recorded in the execution registry, so a direct `Invoke` cannot run an arbitrary journey. The sweep runs one durable step per page of users and resumes after an invocation timeout instead of starting over. A failed instance drops its wake subscriptions.
  - **Actions carry no `codeHash`, and there is no `ActionVersionPolicy`.** The hash was of `handler.toString()`, which every bundler prints differently, so each toolchain produced a "new version" of every workflow with a `.run()`. `action(name, handler)` is unchanged; `compileBundle` checks the action a workflow runs is the definition listed in `actions`; `new RegistryActionInvoker(actions)` takes no policy; `plan()` lists actions as added or removed.
  - **`plan()` keys templates by channel and id**, so an email and a push sharing an id no longer report `changed` forever.
  - **Compile refuses** a `.sendEvent()` carrying literal fields a strict event does not declare, `timeWindow({ days: [] })`, `performed({ count: 0 })`, zero durations and segment reference cycles.
  - **The `scheduled` handler awaits the sweep** instead of handing it to `waitUntil`, so a long sweep is not cut off silently.
  - **Provider credentials are kept by the host**, not per run: one APNs provider token and one FCM access token per warm Worker or Lambda, whatever env object a run hands in, and never a cached template renderer.
  - **Tracking serves only current links.** The `/t/c/` route and `legacyUnsubscribeUrl` are gone; an unsubscribe returns the recipient from its own transaction (`recordUnsubscribe` → `{ userId } | undefined`).
  - **APNs identifies a copy by one UUID** (`apns-id` and `apns-collapse-id` both), hashed from the whole idempotency key, so two push nodes of one long-named instance never collapse into one notification.
  - The AWS handler retries a transient registry read a few times before failing the execution; the sweep's page cursor is compared for equality only, so a store's own collation cannot be misread as "not advancing".
  - **Push credentials are objects of their own.** `ApnsProviderToken`, `FcmAccessToken` and `VapidSigner` own their caching and refresh (one in-flight signing or exchange for concurrent sends, `invalidate()` on an expired or revoked token); `ApnsPushSender`, `FcmPushSender` and `WebPushSender` take them as `credentials` and are built per run. The senders' `onUnregistered` option is gone: the host removes a device from the settled reason.
  - **The host is organized by role.** `@shware/workflow/cloudflare` keeps the same names, but inside the package the runtime port (`JourneyEnv`, `JourneyParams`, `WorkflowBindingLike`, `InstanceNotFoundError`) lives in `host/platform`, the ingest domain in `host/ingest`, and the whole HTTP surface in one declarative route table (`host/http`: `serve` for the host, `handleRequest` for the bare API). A wrong method on a known path answers 405; an unknown path 404 whatever the bearer. `isInstanceNotFound` (a regex over error text) is replaced by `cloudflareJourneyBinding`, which maps Cloudflare's `instance.not_found` to `InstanceNotFoundError`; `AwsInstances` throws it already.
  - **Erasure API.** `JourneyStore.erasureState(userId)` → `'none' | 'erasing' | 'erased'` replaces `erasurePending`; `forgetUser(userId, at)` marks the tombstone `erased_at` instead of deleting it; `UserErasedError` is the store's. `JourneyReporting.recordUnsubscribe` answers `{ userId } | undefined`.
  - `scaleDurations` walks the IR by structure: a message prop or an emitted payload shaped like a duration is left alone.

### Patch Changes

- da8ebed: Classify delivery failures the way the providers document them. Only a token APNs (`Unregistered`, `ExpiredToken`, 410) or FCM (`UNREGISTERED`) reports as gone removes the device; a configuration error (`DeviceTokenNotForTopic`, `SENDER_ID_MISMATCH`, a bad topic) fails the step without retrying and keeps the device, and APNs' `BadDeviceToken` (a token, or the other environment) and FCM's `INVALID_ARGUMENT` settle the copy undelivered with the device kept. Other 4xx answers from APNs, FCM, Web Push, a message webhook, or a missing channel configuration are `PermanentError`s the step does not retry; 429 and 5xx still are. SES throttling reported as a 400 (`Throttling`) is retried. An expired APNs provider token or FCM access token is refreshed instead of reused on the retry. APNs requests carry `apns-id` and `apns-collapse-id`, Web Push a `Topic`, so a resend after a lost checkpoint collapses on the device. A Web Push payload over 3993 bytes (RFC 8291 §4, one 4096-byte record) is refused before it is encrypted. Provider senders are kept per isolate, so the APNs JWT and the FCM access token are reused across runs.

## 3.1.0

### Minor Changes

- 1f5a21c: Fix five correctness problems in the AWS durable Lambda adapter. Postgres hosts must migrate: regenerate the drizzle schema (`workflow-ui generate`) for the new `version` column on `trigger` and `segment_trigger` and `stopped_at` on `execution`, and run the migration before deploying.

## 3.0.0

### Major Changes

- 401288f: Run journeys on AWS Lambda durable functions, and choose the email provider independently of the runtime.

  - New `@shware/workflow/aws`: `journeyLambda({ config, env, store, email })` returns one handler for a durable function behind a Function URL. HTTP requests (the same API as the Worker) and internal runs are told apart by the event's top-level shape, so a request body can never pass for a run. Each journey instance is its own durable execution, started by an asynchronous invoke of the function's own numbered version under a stable execution name; steps, delays and waits map onto the durable SDK's `step`, `wait` and callbacks, with each wait parking on a fresh callback recorded in Postgres. A `{ "type": "$workflow.sweep" }` event runs the segment sweep plus maintenance: unconfirmed starts are retried with the same name and payload (until `startRetryMs`, 12 hours by default, then left unresolved), and executions the platform ended on its own are recorded as failed. `POST /deploy` of an arbitrary bundle is refused; each published version makes its own bundle live. `@aws/durable-execution-sdk-js` and `@aws-sdk/client-lambda` are optional peer dependencies.
  - Email is split into a shared `EmailSender` (render, tracking, tracked-link commit) and a transport: `sesEmailTransport` (`@shware/workflow/transports/ses`, SES v2 over a SigV4-signed `fetch`, Worker and Node alike, credentials read at send time) and `cloudflareEmailTransport` (`@shware/workflow/transports/cloudflare-email`, the `send_email` binding or the REST API). `CfEmailSender` is removed.
  - `journeyWorker` takes an `email` option and no longer reads `env.EMAIL` by itself. Migrate: add `email: (env) => cloudflareEmailTransport({ binding: env.EMAIL })` to keep Cloudflare Email, or `sesEmailTransport(...)` to send through SES. Without it the email channel fails its sends, saying so.
  - Postgres gains an `execution` table (the start recorded with its entry, and the callback each wait parks on). Regenerate the drizzle schema (`workflow-ui generate`) and run your migrations before deploying; `POST /bundle/deploy` reports the missing table otherwise.
  - `EngineStep.subscribe` receives the wait's `{ deadlineMs }`; adapters that do not need it ignore it. A `WorkflowBindingLike` may implement `plan`, `resume` and `maintain` for a runtime whose starts are retryable submits.
  - APNs pushes from Node go over a built-in HTTP/2 client (shared with `@shware/workflow/apns-relay`).

- cea4727: Add `.prefer([pushTemplate, emailTemplate], props, { label })` to the flow builder: one message on the first reachable channel, compiled to the same branch (IR, ids and hash) as writing `branch([reachable(first), …], second)` by hand, with both templates required to declare the same props type.

## 0.1.0

### Minor Changes

- f9db1db: One flat `workflow.config.ts` for the whole project: `defineConfig({ title, contract, workflows, segments, actions, templates: { email, push }, emails: { from, replyTo }, runtime, apns, fcm })` registers everything once — what is deployed, the template registries, the contract, the email envelope and how the engine runs per mode. `compileConfig(config)` builds the bundle with the template manifest taken from the registries and checks every message node (an unregistered or cross-channel template, a literal prop the schema refuses, a missing required prop, a user ref the contract's profile does not declare → `ConfigCompileError` naming the workflow and node). `journeyWorker({ config, store, devices })` serves that bundle at `/bundle` and `/bundle/deploy`, assembles the email sender, the per-platform push senders (`ApnsPushSender` for `ios`, `FcmPushSender` for `android`), the template validator, `/preview` and the runtime from it, and validates ingest with its contract. Secrets come from the environment under fixed names (`APNS_PRIVATE_KEY_BASE64`, `GOOGLE_APPLICATION_CREDENTIALS_BASE64`, `API_TOKEN`, dev-only `APNS_RELAY_ORIGIN`) and `ENVIRONMENT` picks the mode. Template keys are unique per channel, so an email and a push may share one.
- f9db1db: Shared Zod contracts: `defineContract({ events, profile })` turns event payload schemas and a flat profile schema into the DSL's reference tables (`contract.events`, `contract.user` — declared fields only, so a loose object's extra keys are not spellable) plus `eventNames`, `parseEvent` and `parseProfilePatch` (merge-patch semantics: omitted keeps, `null` removes, provided values checked, undeclared refused). `new JourneyClient({ contract })` types `track` / `identify` by event name and refuses bad input before sending (`JourneyValidationError` with field paths); `journeyWorker({ contract })` re-validates every `/events` and `/identify` and answers 400 before anything is stored, woken or started (`contractMode: 'report'` logs instead, for checking producers first). Unsupported schemas (defaults, transforms, coercion, custom or async checks, nested profile fields) are refused when the contract is defined. `UserPropertyBase.email` is now optional.
- f9db1db: Breaking: the Postgres store keeps its tables in a schema of its own, `workflow` unless `defineConfig({ database: { schema } })` names another, with short table names and no prefix (`tablePrefix` and `postgres-schema.sql` are gone). The tables are declared once in the SDK (`TABLES`): `renderDrizzleSchema(schema)` writes them as one drizzle file (`pgSchema(...)`, every table `workflowSchema.table(...)`, UUID v7 checks, timestamptz, no database defaults) for the host to migrate with its own drizzle-kit, and `renderPostgresDdl` as plain DDL. `journeyWorker`'s `store` callback receives the config's `{ schema }`, and `POST /bundle/deploy` first checks the live database against the declared tables (`PostgresJourneyStore.checkSchema`, read-only), answering 503 with every missing table or column instead of deploying.
- f9db1db: Add `unbindDevice` (store, `POST /devices/unbind`, `JourneyClient.unbindDevice`): signing out keeps the device registered with no user (`device.user_id` is now nullable) instead of removing it, so the next sign-in only binds it again; the former owner's device waits wake. `removeDevice` stays for tokens the push service reports gone. Regenerate the schema and migrate; a D1 database created with `devices.user_id NOT NULL` needs the table rebuilt.
- f9db1db: Unsubscribing now suppresses the channel: the unsubscribe link records a `suppression` row for the user, later email steps for that user are skipped, and `reachable(email)` reads false; `/t/u` answers 404 for an unknown copy.
- f9db1db: `.use(fragment)` splices a `flow(...)` or a callback into the chain while the workflow is defined: no new IR node, ids assigned over the whole workflow as if written inline (same executable IR and hash), one copy per use so a fragment is reusable across places and workflows. Sub-flow callbacks that return a Promise are now refused (they would add nodes after ids were assigned).
- f9db1db: Add `forgetUser(userId)` (client, `POST /users/forget`, and the Cloudflare export) for erasure requests: it deletes the user's profile, events, devices, subscriptions, segment memberships, suppressions, messages and their opens, clicks and links from the store, and terminates the user's running journey instances.
- f9db1db: Conversion is recorded apart from how an instance ends: outcomes and `finished` reports carry `convertedAt` (stored as `instance.converted_at`), so `exitOnMatch: false` keeps its conversion. The goal only counts events inside its window — `performed` gets an upper bound (`untilMs`, through `countEvents`/`listEventPayloads`), so a purchase after `within` closed never converts even when the check runs later — and the wait for the window after the last step also ends on `exitWhen`.
- f9db1db: The conversion window outlives the flow: a journey that has run all its steps while its goal's `within` is still open keeps watching for the goal (anchored at entry) until the window closes, and ends as `goal` when it is met. A purchase after the last offer email now counts as that journey's conversion instead of landing after a plain `completed`. Goals without a window still end with the flow.
- f9db1db: A host is now one call: `journeyWorker(options)` (`@shware/workflow/cloudflare`) returns the runner class and the fetch handler with the store lease lifecycle, `/bundle` + `/bundle/deploy`, `/preview/*` and bearer auth built in. `CfEmailSender` takes an options object (`binding`, `from` / `replyTo` with display names, `render`); the rendered subject is sent as written. New subpaths: `@shware/workflow/postgres-js` (`postgresJsStore`, `postgresJsClient`; `postgres` optional peer), `@shware/workflow/react-email` (`registryRenderer` over the email registry; `react-dom` optional peer) and `@shware/workflow/client` (`JourneyClient` with `identify` / `track` (optional `{ id, ts }` for idempotent retries) / `deploy` for producers such as an api server).
- f9db1db: Instances are reported when they enter (`JourneyObserver.started`, `JourneyReporting.instanceStarted`), before the entry guards: an instance a goal or `exitWhen` ends at once is no longer missing from the reports. `instance.node_id`/`node_at` are nullable and `instanceFinished` upserts; regenerate the schema and migrate.
- f9db1db: IR v2: a workflow's and a segment's identity is `id` (it was `name`, which read like a label; the human label stays `meta.name`). `WorkflowIR.id`, `SegmentIR.id`, the plan's `WorkflowChange.id` / `ResourceChange.id`, `JourneyParams.workflowId`, the store's `listSegments()` rows and the `segment` table's `id` column (D1 `segments.id`). Every contentHash moves, so every workflow redeploys as a new version; IR v1 bundles and stored IRs are not read.
- f9db1db: Breaking: `workflow()` takes one object, `workflow({ id, trigger, goal?, exitWhen?, name?, description? })`, in place of `workflow(name, options)`, matching `segment({ id, ... })`. `id` is the wire identity (still `WorkflowIR.name`, so compiled bundles and hashes are unchanged); `WorkflowOptions` is renamed `WorkflowDefinition`. The unused `tags` and `owner` metadata are removed from the definition and from `MetaIR` (stored bundles that carry them still parse; the fields are dropped).
- f9db1db: Reporting hooks for the host's dashboards: `journeyWorker({ observer })` (a `JourneyObserver`) hears every node an instance reaches (`nodeReached`, in a step of its own so replays do not repeat it), every message copy before and after it goes out (`messagePrepared`, `messageSent`), and how each instance ended (`finished`, including `failed`). Storage stays the host's. `messagePrepared` may return `MessageTracking`, which the built-in senders apply: an email's `http(s)` links are routed through `link` and an open `pixel` is appended (`trackEmail`), a push carries `data` in its payload. `OutboundMessage` now names its `workflow`, `instanceId` and `nodeId`, and a sender may return `{ delivered: false, reason }` — APNs and FCM do for a dead token instead of returning as if delivered.
- f9db1db: iOS pushes without Firebase: `@shware/workflow/apns` (`ApnsPushSender`: token-based APNs provider API, the `.p8` key ES256-signed with WebCrypto, dead tokens reported through `onUnregistered`) and `routeByPlatform({ ios, android })` to pick the outlet from the platform of the device each copy goes to. APNs is HTTP/2-only and `wrangler dev`'s workerd cannot make an HTTP/2 subrequest (a deployed Worker can), so `@shware/workflow/apns-relay` (`startApnsRelay`, Node) forwards local sends; the sender's `origin` points at it.
- f9db1db: Pushes can be counted when the device has them: with reporting and `WORKFLOW_ORIGIN`, a push carries `delivered_url` and `opened_url` beside `message_id`, and the Worker records `POST /t/d/<message>` as the copy's device delivery (`message.device_delivered_at`) and `POST /t/p/<message>` as a person's open — for clients that report on their own, such as an iOS notification service extension or a browser's service worker. An APNs push with a `delivered_url` (or an image) is sent `mutable-content`, so the extension runs.
- f9db1db: Push devices live in the engine's store: the app registers each token with `JourneyClient.registerDevice(userId, { token, platform })` (`POST /devices`) and forgets one with `removeDevice(token)` (`POST /devices/remove`). A token belongs to the last user it was registered for, and tokens APNs / FCM report as gone are removed. A push node sends one copy per device (idempotency key per token), or only the most recent with `.push(t, props, { devices: 'latest' })`; a user without a device is skipped. `reachable('push' | 'email' | …)` branches and waits on reachability, woken by every registration and removal. Push senders are now built on their first message, so a missing APNs key no longer fails email-only journeys. The profile's `push_token` / `push_platform` convention is gone.
- f9db1db: `forgetUser` is a recoverable erasure: the request is recorded (`erasure` table), every running instance is stopped, and only then is the data erased, the request with it. An instance that will not stop leaves everything in place and answers `erased: false`; the scheduled sweep retries pending erasures. A failure to terminate is no longer taken for an instance that is already gone. Store API: `requestErasure`, `pendingErasures`, `runningInstances`, and `forgetUser` now returns nothing.
- f9db1db: Reporting is built in on Postgres: `PostgresJourneyStore.reporting` records where each instance stands and how it ended, every message copy, and the opens and clicks on it, and `journeyWorker` installs it as the default observer. With `WORKFLOW_ORIGIN` set, journey emails' links and open pixel are tracked through the Worker's own `/t/...` routes: every open and click is classified as a person's or a machine's — strong signals alone (scanner user agents, cloud and security-vendor networks, Apple Mail Privacy Protection, HEAD requests, three or more links or every link within seconds, which reclassifies the burst's earlier clicks too), weak ones only together (a click within `emails.tracking.quickClickMs` of delivery, 1 s by default, plus a second link within seconds), with the request's network (ASN, organization, country, never the address) stored beside each verdict — clicks redirect only to the recorded URL, and the config's `emails.unsubscribe` link asks for confirmation before it records the unsubscribe. A push carries its `message_id`; `JourneyClient.messageOpened(userId, messageId)` (`POST /messages/opened`) records the tap. `sweepSegments` (`journeyWorker(...).sweep`, `scheduled`, `POST /segments/sweep`) keeps every deployed segment's membership, starts the journeys of segments entered by the clock alone and snapshots each segment's size; it replaces `evaluateSegmentTriggers`. A segment trigger starts journeys for users who enter after it is deployed.
- f9db1db: Review fixes: `u.userId` now reads the user's own id (it is never stored in the profile); events a journey emits with `.sendEvent()` pass the same contract check as `/events` (an undeclared event, a bad literal or a missing field also fails `compileConfig`; a refusal at run time ends the step without retries), and `.sendEvent()` only accepts scalar payload fields, in the types and when the workflow is defined; contracts accept an explicit list of schema types and walk every container (tuple, intersection, record, catchall), and both contracts and templates refuse value-changing checks (`.overwrite`, `.trim`, `.toLowerCase`, …) as well as custom refinements; `/preview/<key>` takes its props as `?props=<JSON>`, so number and boolean fields can be previewed.
- f9db1db: Schema-driven templates: `emailTemplate({ title, description, props, subject, preview, component })` and `pushTemplate({ title, description, props, preview, content })`, exported from the core entry (no React). The required Zod `props` (a strict object of string / number / boolean / enum / literal fields, optionally `.optional()`) is the only source of the props type — DSL arguments, preview and the component/content parameter derive from it — and is enforced at run time: the preview at declaration, and every send after user refs resolve, through a new `MessageValidator` port that `journeyWorker` builds from its registries (`registryValidator`), so normal senders, custom senders and the dev log all see only parsed props, and a push is validated before its first device. Failures throw `TemplateValidationError` (`phase: 'props'` — component/content never called; `'content'` — the notification returned is invalid) with the instance and node in the message, and the Cloudflare step ends without retries. `templates<Emails, Pushes>()` types both registries (`t.push(key)`). Registries hold only these definitions: the legacy module shapes (a default-exported email component with a `{{ user.x }}` subject, push strings with `{prop}` placeholders), `emailSubject`, `fillSubject`, `fillProps` and `CfEmailSender`'s profile lookup are removed. The renderers render email components as elements (hooks and context work) and send the subject and the push content exactly as the template returns them.
- f9db1db: Breaking: `segment()` takes one object, `segment({ id, name?, description?, condition })`, in place of `segment(name, condition, { name, description })`. `id` is the wire identity (still `SegmentIR.name`, so compiled bundles and hashes are unchanged), and `SegmentRef` exposes it as `id`; `name` and `description` are optional labels outside the hash. `SegmentDefinition` is exported.
- f9db1db: Segment-entry starts are tracked per workflow (`segment_start` table, written with the membership): a start that fails is retried by the next evaluation instead of being hidden behind the membership, and one failing workflow no longer blocks the others on the same segment. One user's failure no longer stops the sweep. Store API: `addSegmentMember` takes the workflows, plus `pendingSegmentStarts` and `completeSegmentStart`.
- f9db1db: In fast-forward the store's segment definitions are read through `scaleSegmentWindows`, so a segment's windows shrink with the journeys and triggers that use it.
- f9db1db: Breaking: template references are derived from the registries themselves. `templates(registry)` takes `{ email?, push? }` — the same object the config registers as `templates` — and returns plain reference tables, `t.email.<key>` / `t.push.<key>`, each typed by its own template's `props` schema; an unregistered key, a channel the registry leaves out, or a template registered under the wrong channel fails to compile, and the last one also throws a `TypeError` naming the key. References are `{ channel, key }` built from the registry's own keys: no template is rendered and the registries are not touched. One `TemplateRegistry<E, P>` type serves both the config's `templates` and `templates()` (the config's `TemplateRegistries` is gone); its channels are optional and an annotated registry keeps its exact keys. The type-only `templates<Emails, Pushes>()` with `t.email('key')` is removed; `template.email(key)` and the other low-level factories stay. The studio fixtures, the playground and the Cloudflare demo use the new shape (`src/email`, `src/push`, `src/templates.ts` exporting `registry` and `t`).
- f9db1db: Browser push: `@shware/workflow/webpush` sends standard Web Push (VAPID, `aes128gcm`) to Chrome, Edge, Firefox and Safari 16+ with nothing but WebCrypto, and `generateVapidKeys()` makes the key pair. A `web` device is the browser's `PushSubscription` JSON, registered like an app token (`registerDevice(userId, { token, platform: 'web' })`); `defineConfig({ webPush: { subject } })` turns the channel on with `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` from the environment. Push templates may give a `url` (where a tap leads; APNs and FCM carry it too).
- f9db1db: `discordTemplate` and `slackTemplate`: messages posted to a team channel through an incoming webhook, declared like email and push templates (a zod `props` schema, a `preview`, a pure `content`) and referenced as `t.discord.<key>` / `t.slack.<key>`. Discord content is typed by `discord-api-types` (content, embeds, …), Slack's by `@slack/types` (Block Kit). The webhook URL stays in the environment: `webhook: (env: Env) => env.WEBHOOK_DISCORD_SALES`, read at send time from the values `journeyWorker({ env: schema })` validated with zod when the Worker first ran — an invalid environment answers 500 listing every variable at fault (never its value). Delivery is plain fetch (`@shware/workflow/webhooks`); a deleted webhook or archived channel settles the message undelivered, a rate limit throws to retry. Slack and Discord messages no longer read a per-user `slack_user_id` / `discord_user_id`.
- f9db1db: Add `webPush.openedEvent`: a notification tap a browser reports to `/t/p` is also ingested as that contract event (`{ message_id }`, one per copy), so conditions such as `performed(e.push_opened)` see web opens as they see the app's.

### Patch Changes

- f9db1db: The scanner and datacenter patterns match whole words, so ordinary user agents and providers containing those letters (for example CUBOT devices) are no longer marked as machines.
- f9db1db: `registryRenderer` streams the email and waits for every Suspense boundary before returning the HTML, so react-email's `<Tailwind>` (which suspends while compiling classes) renders on the Worker; a component that throws rejects the render.
- f9db1db: The validated environment from `journeyWorker({ env })` is used everywhere — the fetch handler, the segment sweep and the workflow runner — and an invalid environment answers 500 instead of crashing with an opaque error.
- f9db1db: `postgresJsStore` closes its connection after 2 seconds idle (`idle_timeout`, overridable through `connection`). A journey run lasts as long as its sleeps and waits, and holding the connection through them held one per sleeping instance — a few hundred in-flight journeys exhausted the database's connection slots.
- f9db1db: A push sends each device in its own durable step, so a failure on one device retries that device alone and the copies already delivered are not sent again.
- f9db1db: Instances checkpointed before conversions were recorded apart replay safely (an old guard result is not taken for a conversion, an old wait check's `false` does not end the wait), and one erasure failing no longer stops the scheduled sweep.
- f9db1db: Template props schemas also refuse custom refinements and value-changing checks placed on the `.optional()` wrapper itself (`z.number().optional().overwrite(...)`), not only on the wrapped type.
- f9db1db: Tracked links are stored before the email is sent (`MessageTracking.commit`), so an instant click always finds its link; opens and clicks are recorded in one locked transaction with the bot judgement, so concurrent scanner clicks are classified together and backdated consistently; a failure reporting a message as sent no longer fails and retries the send step.
- f9db1db: Discord and Slack webhook senders settle a copy undelivered on any permanent 4xx (not 408 or 429) instead of throwing, so a message the channel rejects is never retried.
- f9db1db: Web push subscriptions are validated before sending (an https endpoint, a 65-byte uncompressed P-256 key and a 16-byte auth secret); a malformed one is reported unregistered and removed instead of failing the step, and unregistered tokens on any channel are removed through the configured store.
